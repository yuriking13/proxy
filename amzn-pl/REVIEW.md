# Разбор базовой инфраструктуры Amazon P&L — для автора первой версии

Это встречная проверка твоей работы и внесённые правки. Ниже — что оказалось
сломано, как это воспроизвести, что изменено и что осталось спорным. Всё, что
утверждается, проверяется командами из раздела «Как проверить» — прогони их,
прежде чем соглашаться.

Общая оценка: каркас сделан правильно. Разделение `engine` / Edge Function /
RLS, `commission_rates` без политик, 404 вместо 403 для чужого проекта,
`engine_version` в журнале, синк движка через CI-diff — это верные решения, и
они сохранены. Проблемы оказались в двух местах: финансовая логика cash flow и
несколько утверждений README, не подкреплённых кодом.

---

## 1. Критично: cash flow терял часть закупки

`engine/src/index.ts`, старый цикл cash flow:

```ts
const buyIdx = m + leadShiftMonths;                       // месяц, под который закупаемся
const boughtUnits = buyIdx < inputs.monthlyUnits.length
  ? inputs.monthlyUnits[buyIdx]
  : 0;
```

Цикл идёт по `m` от 0. Закупка под продажи месяца `k` должна происходить в
месяц `k - leadShift`. Для первых `leadShift` месяцев это отрицательный индекс,
которого цикл не достигает — и эта закупка не оплачивается **никогда**.

Воспроизведение на входах из твоего же теста (`leadTimeDays: 45` →
`leadShift = 2`, план `[200,300,400,500,600,700]`):

| | было | должно быть |
|---|---|---|
| закуплено единиц | 2200 | 2700 |
| COGS в cash flow | 16 500 | 20 250 |
| `requiredCapital` | **3 075** | **7 361.67** |
| `paybackMonth` | **5** | **6** |

Необходимый капитал занижался в 2.4 раза. Для калькулятора, который продаётся
ради ответа на вопрос «сколько денег нужно на старте», это самая дорогая из
возможных ошибок: пользователь заходит в проект недофинансированным.

Почему тесты не поймали: они проверяли знак (`requiredCapital > 0`) и
внутреннюю согласованность cash flow с самим собой. Обе проверки проходят на
неверных числах.

### Что добавлено, чтобы это не повторилось

```
последний cashFlow.cumulative == последний monthlyPnl.cumulativeProfit
                                 - upfrontInvestment
```

Сдвиги во времени переставляют платежи между месяцами, но не меняют их сумму,
поэтому к концу горизонта касса обязана сойтись с накопленной прибылью. На
старом коде инвариант нарушался ровно на 3750 — на пропавший COGS. Проверяется
на 8 сценариях в двух режимах времени.

Исправление: платежи вне горизонта прижимаются к границам, а не отбрасываются
(закупка «до старта» попадает в первый месяц — раньше старта проекта денег
потратить нельзя).

## 2. Критично: отсрочка выплат Amazon исчезала

```ts
const payoutShiftMonths = Math.round(inputs.payoutDelayDays / 30);
```

`Math.round(14 / 30) = 0`. Типовая отсрочка выплат Amazon — 14 дней — давала
сдвиг 0 месяцев и полностью пропадала из расчёта. Ты это отметил в README
(«14 дней → 0 месяцев, сверить»), но пометка в README не мешает считать
неправильно: заказчик получает заниженный требуемый капитал и не знает об этом.

Сделано: `TimingPolicy`. По умолчанию платёж разносится между двумя соседними
месяцами пропорционально (14 дней ≈ 0.467 месяца → 53.3% в месяц продажи,
46.7% в следующий). Твой режим сохранён как `wholeMonths` и покрыт тестами —
если Excel-модель заказчика округляет, переключение делается одной константой
`DEFAULT_TIMING`, а не переписыванием цикла.

Почему дробный режим сделан умолчанием: неверный ответ хуже, чем ответ,
отличающийся от Excel на известную величину. Но выбор режима — вопрос к
заказчику, он вынесен в README.

## 3. Округлённые ставки в агрегатах

```ts
const amazonFees = units * (ue.referralFee + inputs.fbaFeePerUnit);
```

`ue.referralFee` уже округлён до копеек в `calcUnitEconomics`. Умножение
округлённого значения на количество накапливает ошибку пропорционально числу
единиц: при ставке, дающей 8.3333 на единицу, и 1000 единиц расхождение с
Excel — 3.33 за месяц. Excel так не считает.

Сделано: агрегаты считаются от неокруглённых величин, округление только на
выходе. Есть тест на ставке 1/3.

## 4. README обещал защиту, которой не было

```yaml
- name: Verify no engine code in frontend bundle (пример; включить после ...)
  run: echo "grep -R 'contributionMargin\|referralFee' frontend/dist && exit 1 || true"
```

Шаг всегда зелёный: это `echo` строки, а не выполнение grep. При этом README
утверждал: «CI-шаг грепает фронтовый бандл на маркеры движка» — как факт, в
списке работающих мер защиты. Это опаснее отсутствия проверки: заказчик,
читающий README, считает контур закрытым.

Отдельно: сами маркеры выбраны неудачно. `referralFee` и
`contributionMarginPerUnit` — поля ответа API, фронт обязан их отображать.
Такой grep падал бы на каждой корректной сборке.

Сделано: `scripts/check-frontend-bundle.sh` с двумя контурами — импорты движка
в исходниках фронта и строковые литералы движка в бандле (`wholeMonths`,
`daysPerMonth`, `calcUnitEconomics`, `ENGINE_VERSION`; строковые литералы
переживают минификацию, имена функций — нет). Поля ответа API из списка
исключены. Пока каталога `frontend/` нет, скрипт печатает предупреждение и явно
сообщает, что контур неактивен — README теперь говорит то же самое.

## 5. База данных

- **Гранты поверх RLS.** Supabase раздаёт широкие привилегии на новые таблицы в
  `public`. RLS без политик закрывает строки, но одна ошибочно добавленная в
  будущем политика открыла бы `commission_rates` целиком. Добавлены явные
  `revoke` — второй независимый слой.
- **Пересекающиеся периоды ставок.** `unique (category, valid_from)` не мешал
  завести `home` с 2025-01-01 бессрочно и `home` с 2025-06-01: запрос «ставка
  на сегодня» отдавал бы произвольную из двух, и расчёт становился
  недетерминированным. Добавлен `exclude using gist`. Следствие: смена ставки
  требует сначала закрыть текущий период — процедура одной транзакцией описана
  в `seed.sql`.
- **`projects.inputs` без ограничения размера.** Клиент пишет туда напрямую
  через PostgREST, то есть строка проекта была неограниченным файловым
  хранилищем на аккаунте заказчика. Добавлен лимит 64 КБ.
- **`search_path` в SECURITY DEFINER.** Было `set search_path = public`;
  `pg_temp` при этом остаётся в неявном поиске. Закреплено как
  `public, pg_temp`.
- **`cleanup_rate_limits()` не вызывалась** — правило хранения было продублировано
  внутри `bump_rate_limit`. Теперь одно определение, `bump` вызывает функцию.
- **`audit_log` не использовалась** ни одной строкой кода. Теперь туда пишутся
  отказы (`license_required`, `rate_limited`, `project_not_found`).

## 6. Edge Function

- Владение проектом проверялось выборкой с последующим сравнением в JS. Теперь
  `user_id` входит в сам запрос — невозможно случайно ответить данными чужой
  строки.
- `Deno.env.get(...)!` падал бы посреди запроса непонятной ошибкой. Обязательные
  переменные проверяются на старте инстанса.
- Добавлены: лимит размера тела, `Retry-After` при 429, `Cache-Control:
  no-store` (результаты персональны и лицензионно ограничены), guard на
  не-объект в теле запроса.
- `corsHeaders` импортировался и не использовался.

## 7. Что добавлено сверх исправлений

**`supabase/tests/security_test.sql` — 23 исполняемые проверки.** У модели
защиты не было ни одного теста, хотя она и есть основной результат работы.
Проверяется под ролями `authenticated` и `anon`: чужой проект не читается / не
меняется / не удаляется, справочник комиссий недоступен, лицензию себе выдать
нельзя, привилегированные функции недоступны, журнал расчётов не подделать.

Тест проверен на способность падать: временное открытие `commission_rates` для
`authenticated` роняет прогон с ненулевым кодом. Тест, который не умеет падать,
бесполезен.

**`migrations/0002` — `grant_license()`.** Это шов, а не интеграция платежей:
ни ключей, ни webhook-эндпоинта, ни SDK. Функция идемпотентна по
`(source, external_id)` и продлевает лицензию от её текущего окончания, а не с
сегодняшнего дня.

Обоснование, почему это в базовой инфраструктуре при том, что платежи спорны по
скоупу: идемпотентность — единственная часть, которую больно добавлять задним
числом. Провайдер повторяет webhook при таймауте, и без ключа идемпотентности
повтор выдаёт вторую лицензию на тот же платёж; ретрофит на живых данных — это
ручной разбор задвоенных лицензий. Если заказчик подтвердит, что выдача
остаётся ручной, миграция удаляется целиком и ничего за собой не тянет.

Также в CI добавлены `deno check` и `deno lint`: Edge Function раньше не
компилировалась в CI вообще, ошибка типов обнаруживалась только при деплое.

## 8. С чем я согласен и что намеренно не трогал

- Копия движка в `_shared/engine` со синком скриптом и diff в CI — при
  ограничениях `supabase functions deploy` это правильный компромисс.
- Отсутствие функции `license-status`: чтение статуса прямым SELECT через RLS
  экономит функцию и не ослабляет защиту.
- 404 вместо 403 для чужого проекта.
- `jsonb` для inputs/results и `engine_version` в журнале.
- Rate limit в Postgres без внешнего KV.
- Формулы каркаса не заменялись: Excel-модели заказчика нет, выдумывать
  формулы вместо переноса — хуже, чем оставить явно помеченный каркас.

## 9. Вопросы, на которые нужен ответ заказчика

1. **Платежи в скоупе?** В объявлении сказано двумя способами: «Подключение
   Stripe и Robokassa (аккаунты готовы)» в списке работ и «настройка Stripe и
   Robokassa» в списке «не требуется». Прочтения дают разный объём работ. Это
   единственный пункт, способный изменить оценку.
2. **Режим округления сроков** — дробный или как в Excel (`wholeMonths`).
   Разница в `requiredCapital` существенная.
3. **`storagePerUnitMonth` в юнит-экономике** сейчас входит как расход на
   единицу, то есть неявно предполагается, что единица лежит на складе ровно
   месяц. Так ли в Excel?
4. **Структура справочника комиссий.** У Amazon есть категории с зависимостью
   ставки от цены и минимальным referral fee (обычно $0.30). Если это есть в
   Excel-модели, схема расширяется.
5. **Ретеншн `calculations`** не задан — журнал растёт без ограничений.

## Как проверить

```bash
bash scripts/sync-engine.sh
node --experimental-strip-types --test engine/tests/*.test.ts   # 44 теста
bash scripts/test-db.sh                                          # 23 проверки, нужен postgres
bash scripts/check-frontend-bundle.sh
```

Проверить, что тест защиты умеет падать:

```bash
cat >> supabase/migrations/0001_init.sql <<'SQL'
grant select on public.commission_rates to authenticated;
create policy tmp_leak on public.commission_rates for select to authenticated using (true);
SQL
bash scripts/test-db.sh   # должен упасть на «справочник комиссий недоступен»
git checkout supabase/migrations/0001_init.sql
```

Проверить исходный дефект cash flow: в `engine/src/index.ts` переключить
`DEFAULT_TIMING.mode` на `"wholeMonths"` — числа сойдутся с твоей версией по
срокам, но COGS всё равно будет учтён полностью, потому что исправление
прижатия платежей к границам горизонта от режима не зависит.

## Замечание по миграциям

`0001_init.sql` изменён на месте, а не дополнен миграцией `0002`. Это осознанно:
схема ещё нигде не развёрнута, и отдавать заказчику две миграции, где вторая
чинит первую, хуже, чем одна корректная. Если у тебя `0001` уже применён на
dev-проекте Supabase — базу нужно пересоздать (`supabase db reset`).

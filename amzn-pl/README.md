# Amazon P&L Calculator — базовая инфраструктура

Задача (по ТЗ заказчика): вынести расчётную логику из frontend в Supabase Edge
Functions, добавить Auth по email, лицензионный доступ, RLS. Дизайн и продающий
сайт — вне скоупа.

## Структура

```
engine/                      расчётный движок (чистый TS, источник истины)
  src/index.ts               формулы: unit economics, помесячный P&L, cash flow,
                             requiredCapital, payback
  src/validate.ts            валидация входов (без зависимостей)
  tests/engine.test.ts       инварианты каркаса; при переносе — эталоны из Excel
supabase/
  migrations/0001_init.sql   схема + RLS + rate limit + лицензии
  migrations/0002_*.sql      идемпотентная выдача лицензий (шов под платежи)
  functions/calculate/       единственная точка расчёта
  functions/_shared/         cors, http, копия engine (см. scripts/sync-engine.sh)
  tests/security_test.sql    исполняемые тесты RLS и прав доступа
  seed.sql                   демо-справочники + процедура смены ставки
  config.toml                verify_jwt=true для calculate
frontend-snippets/api.ts     интеграция фронта (auth, лицензия, вызов расчёта)
scripts/test-db.sh           миграции + тесты защиты на чистой базе
scripts/check-frontend-bundle.sh  движок не должен попадать в бандл
```

CI лежит в корне репозитория: `.github/workflows/amzn-pl-ci.yml`.

## Проверка

```bash
bash scripts/sync-engine.sh
node --experimental-strip-types --test engine/tests/*.test.ts   # 44 теста
bash scripts/test-db.sh                                          # 21 проверка
bash scripts/check-frontend-bundle.sh
```

## Модель защиты (ответ на вопрос №3 из ТЗ)

1. **Формулы и справочники существуют только на сервере.** Движок исполняется в
   Edge Function; `commission_rates` закрыта и RLS без политик, и явным
   `revoke all` — тест проверяет, что `authenticated` получает
   `permission denied`.
2. **Без активной лицензии расчёт недоступен**: `has_active_license()` до
   расчёта, 403 `license_required`. Функция доступна только `service_role` —
   пользователь не может ни вызвать её, ни выдать лицензию себе (проверено
   тестом).
3. **Чужие проекты недоступны**: RLS `user_id = auth.uid()` на всех
   пользовательских таблицах. В Edge Function (service_role обходит RLS)
   владение входит в сам запрос (`.eq("user_id", userId)`), чужой проект отдаёт
   404, а не 403 — существование ресурса не раскрывается.
4. **service_role key** живёт только в секретах Edge Functions.
5. **Rate limit** 30 расчётов/мин (env `RATE_LIMIT_PER_MIN`), ответ 429 с
   `Retry-After`. Превышение пишется в `audit_log` один раз на окно.

### Честные границы этой защиты

Их стоит проговорить заказчику до начала работ, а не после.

- **Ответ API раскрывает производные значения.** В `unitEconomics` возвращается
  `referralFee`; поделив его на цену, клиент получает ставку комиссии по своей
  категории. Спрятать это нельзя — фронт обязан показывать разбивку расходов.
  Rate limit ограничивает скорость снятия справочника, но не делает это
  невозможным.
- **Чёрный ящик аппроксимируем.** Достаточное число расчётов позволяет
  восстановить модель регрессией. Это ограничение любого SaaS-калькулятора, а
  не конкретно этой реализации.
- **Проверка бандла активируется только вместе с фронтом.** Пока каталог
  `frontend/` не подключён к репозиторию, `check-frontend-bundle.sh` печатает
  предупреждение и не проверяет ничего. Это осознанная заглушка, а не
  работающий контур.

## Деплой (аккаунты заказчика)

```bash
supabase link --project-ref <ref>
supabase db push
psql "$DATABASE_URL" -f supabase/seed.sql        # затем заменить реальными ставками
supabase secrets set ALLOWED_ORIGINS=https://<домен-netlify>
bash scripts/sync-engine.sh
supabase functions deploy calculate
```

Фронт: задать `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` в Netlify,
подключить `frontend-snippets/api.ts`, вырезать расчётные модули из бандла.

Выдача лицензии:
```sql
select public.grant_license('<uuid>', 30, 'manual', null, 'ручная выдача');
```

## Принятые решения

- **jsonb для inputs/results** — формулы будут меняться; `engine_version` в
  `calculations` делает старые результаты воспроизводимыми.
- **Копия движка в `functions/_shared/engine`** — `supabase functions deploy`
  пакует только каталог functions; синк скриптом, расхождение ловит CI (diff).
- **verify_jwt=true + ручная проверка `getUser`** — двойной контур; если
  верификация на шлюзе помешает preflight (OPTIONS), её можно отключить в
  config.toml без потери безопасности — своя проверка остаётся.
- **`license-status` функции нет** — статус лицензии фронт читает прямым
  SELECT через RLS (пользователь видит только свои строки), минус одна функция.
- **Rate limit в Postgres (fixed window)** — без внешнего KV, атомарный upsert,
  ленивая очистка старых окон.
- **Дробная сетка cash flow** — см. `TimingPolicy` ниже.

### Почему cash flow считает дробными месяцами

Первая версия округляла задержки до целых месяцев (`Math.round(days / 30)`).
На типовых входах это давало две ошибки сразу:

- отсрочка выплат Amazon 14 дней превращалась в 0 месяцев и исчезала из
  расчёта;
- закупка под продажи первых месяцев приходилась на «отрицательные» месяцы и
  просто выпадала из оттоков — на сценарии из тестов из cash flow пропадало
  3750 из 20250 COGS, `requiredCapital` выходил 3075 вместо 7361.67 (занижение
  в 2.4 раза), окупаемость — 5 месяцев вместо 6.

Сейчас платёж разносится между двумя соседними месяцами пропорционально, а
платежи «до старта проекта» прижимаются к первому месяцу. Инвариант, который
это фиксирует и который проверяется на 8 сценариях в обоих режимах:

```
последний cashFlow.cumulative == последний monthlyPnl.cumulativeProfit
                                 - upfrontInvestment
```

Если Excel-модель заказчика округляет до целых месяцев, поведение
переключается одной константой `DEFAULT_TIMING` в `engine/src/index.ts`
(режим `wholeMonths` сохранён и покрыт тестами). Разница в цифрах
существенная, поэтому режим стоит согласовать с заказчиком, а не выбирать
молча.

## Открытые вопросы к заказчику

1. **Платежи — в скоупе или нет.** В объявлении это сказано двумя способами:
   «Подключение Stripe и Robokassa (аккаунты готовы)» в списке работ и
   «настройка Stripe и Robokassa» в списке «не требуется». Прочтения дают
   разный объём работ, и это единственный пункт, который может изменить
   оценку. Здесь сделан только шов: `grant_license()` — идемпотентная выдача,
   к которой webhook подключается позже (миграция `0002`). Webhook-эндпоинта,
   ключей и SDK нет. Если платежи не нужны — миграция удаляется целиком.
2. **Округление сроков в cash flow** — см. раздел выше.
3. **Структура справочника комиссий.** Сейчас `(категория, ставка, фикс.
   сбор, период)`. У Amazon есть категории с зависимостью ставки от цены и с
   минимальным referral fee (обычно $0.30) — если это есть в Excel-модели,
   схема расширяется.
4. **Админка выдачи лицензий.** По умолчанию — SQL-вызов `grant_license`.
   Отдельная страница администратора — примерно +1 день.

## Что требует сверки при переносе реального проекта

1. Формулы каркаса заменить формулами из Excel/фронта заказчика; на каждый лист
   Excel — golden-тест (входы из Excel → эталонные выходы из Excel).
2. `storagePerUnitMonth` сейчас входит в юнит-экономику как расход на единицу,
   то есть неявно считается, что единица лежит на складе ровно месяц. Сверить с
   Excel.
3. Валидация: `acos` ограничен 500% (на запуске ACoS выше 100% — норма),
   `payoutDelayDays` ≤ 120, `leadTimeDays` ≤ 365, план продаж ≤ 60 месяцев,
   штуки — целые. Границы взяты из здравого смысла, а не из модели заказчика.
4. Ретеншн `calculations` не задан: журнал растёт без ограничений. Если
   расчётов будет много, нужна политика хранения.
